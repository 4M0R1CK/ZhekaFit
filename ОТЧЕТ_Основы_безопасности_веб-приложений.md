## Цель

Проверить обработку пользовательских данных и применить подходящие меры защиты от XSS, CSRF и SQL-инъекций, усилить настройки доступа и подключить проверки безопасности к CI.

## Выполненная работа

1. **XSS и вывод данных.** Интерфейс выводит пользовательские и загруженные из базы значения через React, который экранирует текст при рендеринге. В проекте не используется `dangerouslySetInnerHTML` или ручная вставка HTML. В nginx добавлена CSP: скрипты разрешены только с источника приложения, объекты запрещены, а загрузка стилей, шрифтов, изображений и соединения с Supabase ограничены необходимыми источниками.
2. **SQL-инъекции.** Чтение и изменение данных выполняются через Supabase query builder; бронирование вызывает RPC `book_class_session` с UUID-параметром. SQL-функции используют фиксированный `search_path`, а не собирают запросы из пользовательских строк.
3. **CSRF и сессии.** Приложение использует Supabase Auth и передаёт токен через заголовок авторизации Supabase-клиента; собственных cookie-сессий и cookie-аутентифицированных изменяющих эндпоинтов в проекте нет. Поэтому классическая CSRF-защита с synchronizer-токеном не добавлялась. Клиентская сессия хранится браузерным SDK, поэтому CSP и безопасный вывод важны для снижения XSS-риска. При переходе на серверные cookie-сессии нужно добавить `HttpOnly`, `Secure`, `SameSite` и CSRF-проверку.
4. **Валидация и обработка данных.** Для профиля ограничены длины имени и телефона, набор предпочтений и путь фотографии на уровне базы данных. Форма ограничивает длины полей. Загрузчик принимает только JPEG, PNG, WebP и AVIF до 10 МБ и генерирует непредсказуемое имя файла. Supabase Storage дополнительно ограничивает типы и размер, а RLS разрешает пользователю загружать файлы только в собственный каталог `profiles/<user-id>/`.
5. **Минимальные права.** Пользователь может читать только собственный профиль и изменять только поля, нужные форме. Прямая вставка профиля из клиентского приложения отозвана: профиль создаёт триггер после регистрации. RLS и узкие grants на бронирования и абонементы сохранены.
6. **Защитные HTTP-заголовки.** nginx отправляет CSP, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy` и ограничивающий `Permissions-Policy`. HSTS не включён на внутреннем HTTP-порту контейнера: его следует задавать на публичном HTTPS reverse proxy/балансировщике.
7. **Проверки CI.** GitHub Actions запускает CodeQL (SAST), `npm audit --audit-level=high` (SCA), lint, тесты и production-сборку. Workflow запускается на push, pull request и еженедельно. Dependabot еженедельно проверяет npm-пакеты и GitHub Actions.
8. **Пароли.** Приложение не хранит и не хеширует пароли самостоятельно; регистрация, вход, сброс и смена пароля делегированы Supabase Auth. Ключ `service_role` не используется в браузерном приложении.

## Проверка

Локально выполнены:

- `npm run lint` — успешно;
- `npm run test` — 1 файл, 4 теста успешно;
- `npm run build` — успешно;
- `npm audit --audit-level=high` — 0 известных уязвимостей;
- Docker image собирается; `nginx -t` успешен, главная страница отвечает HTTP 200 с указанными защитными заголовками.

## Применение к Supabase

Файл `supabase/create_database.sql` и соответствующая миграция обновлены. Чтобы новые ограничения базы и права профилей вступили в силу в проекте Supabase, нужно применить repair-скрипт через SQL Editor согласно `supabase/README.md`. Изменения файлов в репозитории сами по себе не меняют уже развёрнутую базу.
